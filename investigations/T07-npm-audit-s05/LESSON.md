# T07 — `npm audit` / S05

## The question

Use `npm audit` against S05 to distinguish:

```text
npm dependency metadata
package source contents
npm lifecycle execution
published package contents
generated runtime provenance
vulnerability matching
```

The central question is:

> When `prepack` generates runtime JavaScript that survives publication while the generator and original input disappear, what can `npm audit` still see?

## The instrument

The observed run used:

```text
Node v26.4.0
npm 12.0.1
registry https://registry.npmjs.org/
```

---

# Ground truth

Every expectation below is derived from this section: what S05 actually
contains and what its packaging actually does, established independently of
the tool under investigation.

## Fixture

S05's tracked component is `trace-route-package 1.0.0`, a local package whose `prepack`
lifecycle hook generates its runtime code at pack time. Four states matter:
the package source before packing, the lifecycle execution itself, the
published tarball, and the provenance evidence the generator deliberately
plants in its output.

## Run

```command
./scripts/baseline-s05.sh
```

## Observed

Before packing, the package source contained:

```output
packages/trace-route-package/build-input/route.json
packages/trace-route-package/package.json
packages/trace-route-package/scripts/generate-dist.js
```

Its `package.json` declares:

```json
{
  "name": "trace-route-package",
  "version": "1.0.0",
  "main": "dist/index.js",
  "prepack": "node scripts/generate-dist.js"
}
```

So before publication, S05 has:

```text
package metadata
generator code
generator input
```

but the runtime `dist/` output has not yet been created.

`npm pack` printed:

```text
npm notice run trace-route-package@1.0.0 prepack
npm notice run node scripts/generate-dist.js
generated dist/index.js for /hidden/prepack-info
generated dist/prepack-evidence.json
```

The tarball contained exactly:

```text
package/dist/index.js
package/package.json
package/dist/prepack-evidence.json
```

It did not contain:

```text
scripts/generate-dist.js
build-input/route.json
```

The published `package.json` still retained the lifecycle declaration:

```text
"prepack": "node scripts/generate-dist.js"
```

even though the referenced script itself was no longer in the package.

Finally, the installed generated evidence file contained:

```json
{
  "event": "npm-prepack-generated",
  "package": "trace-route-package",
  "version": "1.0.0",
  "generatedBy": "npm lifecycle prepack -> scripts/generate-dist.js",
  "message": "This runtime route was generated by an npm prepack lifecycle script.",
  "origin": "trace-route-package build input",
  "route": "/hidden/prepack-info"
}
```

## What this pins down

Packaging is an active transformation:

```text
package source
    ↓ npm prepack
scripts/generate-dist.js executes
    ↓
dist/index.js
dist/prepack-evidence.json
```

The published runtime bytes are not simply a copy of the original package
source. Publication preserved:

```text
generated runtime bytes
generated evidence file
package metadata
lifecycle declaration string
```

while discarding:

```text
generator implementation
original build input
```

So even before vulnerability scanning:

```text
published package
    !=
source package
```

And the final installed package contains explicit evidence that:

```text
prepack executed
generator produced runtime content
runtime route is /hidden/prepack-info
```

This gives us a controlled provenance signal to search for in `npm audit`: if
any audit output can see how the shipped bytes were produced, these strings
are where it would show.

# Running the probes

All eight probes are driven by one script:

```command
./scripts/run-npm-audit-s05.sh
```

The installed application dependency tree established by the baseline was:

```text
node-prepack-trace-lab@1.0.0
└── trace-route-package@1.0.0
```

# Probe 1 — audit the application

## Question

What does `npm audit` report for the installed application?

## Expectation

Ground truth: the application's dependency model contains exactly one
dependency, the local `trace-route-package 1.0.0`, for which no registry
advisory exists. Expect a clean result — and the open question is whether
anything of the package's production history (the prepack execution, the
vanished generator) surfaces alongside it.

## Observed

The application audit produced:

```output
json=true
vulnerabilityRecords=0
dependencyTotal=1
vulnerabilities:
(none)
exit=0
```

## Verdict

**trace-route-package 1.0.0: identified in the dependency model. Its
production history: invisible.** `npm audit` operated on an npm dependency
model containing one dependency and reported no vulnerability for it. The
result did not expose how the installed package's runtime bytes had been
created.

# Probe 2 — ignore `node_modules`

## Question

Does the answer change when the audit explicitly ignores the installed files?

## Expectation

If `npm audit` derives its inventory from dependency metadata rather than from
inspection of the installed `node_modules` tree, ignoring that tree should
change nothing.

## Observed

Running:

```output
npm audit --package-lock-only
```

produced exactly the same audit summary:

```text
vulnerabilityRecords=0
dependencyTotal=1
exit=0
```

## Verdict

**Same result with the installed files ignored**, as expected. For this
scenario:

```text
application audit
    ==
package-lock-only audit
```

This is consistent with npm dependency metadata driving the vulnerability
decision, rather than inspection of the generated installed files.

---

# Probe 3 — audit the source package without a lockfile

## Question

Can `npm audit` audit the package source as it sits on disk?

## Expectation

Ground truth: the source package physically contains `package.json`, the
generator script and its build input — but no lockfile. If a normal audit
requires the lockfile-backed dependency model rather than the files
themselves, it should refuse, however auditable the directory looks.

## Observed

A normal audit in the source package failed:

```output
npm error code ENOLOCK
npm error audit This command requires an existing lockfile.
npm error audit Try creating one first with: npm i --package-lock-only
npm error audit Original error: loadVirtual requires existing package-lock.json file
```

The captured result was:

```text
dependencyTotal=unknown
vulnerabilityRecords=0
exit=1
```

## Verdict

**Refused — ENOLOCK.** The source package's physical contents are not
sufficient input for a normal `npm audit`. It contains:

```text
package.json
scripts/generate-dist.js
build-input/route.json
```

but without a lockfile npm refuses the ordinary audit. So:

```text
files present on disk
    !=
auditable npm dependency model
```

---

# Probe 4 — rebuild the source dependency model from `package.json`

## Question

When npm is told to rebuild the model from package metadata alone, what enters
the inventory?

## Expectation

Ground truth: the source `package.json` declares no dependencies — only the
`prepack` lifecycle hook. Expect zero dependencies; the generator script, its
input and the lifecycle declaration should create no inventory entries.

## Observed

Running the source package with:

```output
--no-package-lock
```

produced:

```text
dependencyTotal=0
vulnerabilityRecords=0
exit=0
```

## Verdict

**Zero dependencies identified**, as expected. When npm rebuilt the model from
the source package metadata, it found no dependencies to audit. The presence
of:

```text
scripts/generate-dist.js
build-input/route.json
prepack lifecycle declaration
```

did not create vulnerability inventory entries.

---

# Probe 5 — audit the published package without a lockfile

## Question

Does the published package — which now physically contains generated runtime
JavaScript — fare any better under a normal audit?

## Expectation

Ground truth: the unpacked tarball has materially different bytes from the
source package, but still no lockfile. Expect the same refusal: the physical
presence of shipped runtime code should not make the package independently
auditable.

## Observed

A normal audit of the unpacked published tarball failed with the same
`ENOLOCK` condition:

```output
This command requires an existing lockfile.
```

Captured summary:

```text
dependencyTotal=unknown
vulnerabilityRecords=0
exit=1
```

## Verdict

**Refused — ENOLOCK**, as expected. The fact that the package now physically
contains generated runtime JavaScript does not make it independently auditable
by `npm audit`. Again:

```text
shipped JavaScript bytes
    !=
npm dependency model
```

# Probe 6 — rebuild the published dependency model from `package.json`

## Question

Rebuilt from metadata alone, does the published package's audit model differ
from the source package's?

## Expectation

Ground truth: source and published packages contain materially different bytes
— generator and input on one side, generated runtime and evidence file on the
other — but their `package.json` dependency declarations are the same. If the
audit model is built from metadata, the two physically different packages
should be indistinguishable to it.

## Observed

Running the published package with:

```output
--no-package-lock
```

produced:

```text
dependencyTotal=0
vulnerabilityRecords=0
exit=0
```

## Verdict

**Zero dependencies identified — indistinguishable from the source package.**
This matters because the source and published packages contain materially
different bytes:

```text
source package
    scripts/generate-dist.js
    build-input/route.json

published package
    dist/index.js
    dist/prepack-evidence.json
```

Yet their `--no-package-lock` audit results were identical:

```text
dependencyTotal=0
vulnerabilityRecords=0
```

So `npm audit` did not distinguish those two physical software states.

# Probe 7 — search audit output for lifecycle/provenance evidence

## Question

Do the provenance signals that ground truth planted appear anywhere in any
audit output?

## Expectation

Ground truth deliberately shipped four searchable strings — the generator
path, the evidence event name, the evidence filename and the generated route.
If any part of the audit pipeline sees how the package's bytes were produced,
at least one of them should surface.

## Observed

Across all S05 audit outputs:

```output
scripts/generate-dist.js     not found
npm-prepack-generated        not found
prepack-evidence.json        not found
/hidden/prepack-info         not found
```

## Verdict

**All four provenance signals: absent.** The source and installed package
contain those provenance signals, but the audit output does not expose them.
This is the key T07 distinction:

```text
npm lifecycle provenance
    !=
npm vulnerability evidence
```

`npm audit` did not reconstruct:

```text
which lifecycle script executed
which generator produced the bytes
which build input was consumed
which runtime route was generated
```

# Probe 8 — prove the vulnerability-advisory path works

## Question

Is the advisory service actually functioning — or are the clean S05 results
just a broken audit path?

## Expectation

The isolated public control uses a package with known advisories. If the
registry audit path works, it must return at least one vulnerability record —
otherwise every clean result above is suspect.

## Observed

The isolated public control used:

```output
lodash 4.17.21
```

The audit produced:

```text
json=true
vulnerabilityRecords=1
dependencyTotal=1
exit=1
```

The vulnerability entry was:

```text
lodash
severity: high
direct
range: <=4.17.23
```

and referenced three advisory causes in the returned `via` data.

## Verdict

**lodash 4.17.21: identified, with a vulnerability record attached.** The npm
registry audit path was functioning and capable of returning current
vulnerability intelligence, so a broken audit service does not explain the
clean S05 results. The control establishes:

```text
known vulnerable npm dependency identity
    → vulnerability result
```

while S05 establishes:

```text
generated runtime provenance
    → no vulnerability inventory entry by itself
```

# Findings

## 1. `npm audit` is dependency-metadata driven

The application and `--package-lock-only` scans returned the same result even
though the latter explicitly ignored `node_modules`.

For S05:

```text
installed files
    did not change
vulnerability result
```

---

## 2. Physical package contents are not enough for ordinary `npm audit`

Both the source package and published package contained meaningful executable
or generated content.

Without a lockfile, normal `npm audit` failed with:

```text
ENOLOCK
```

So:

```text
software bytes present
    !=
npm audit inventory available
```

---

## 3. Source and published packages can look identical to the audit model

The source package contained the generator and input.

The published package contained generated runtime output instead.

Yet:

```text
source --no-package-lock
    dependencyTotal=0

published --no-package-lock
    dependencyTotal=0
```

The audit model did not represent the transformation between them.

---

## 4. Lifecycle declarations are not lifecycle execution evidence

The published `package.json` still says:

```text
"prepack": "node scripts/generate-dist.js"
```

but the actual generator is absent from the tarball.

`npm audit` exposed neither the declaration nor evidence that the lifecycle
script had executed.

Therefore:

```text
lifecycle declaration
    !=
lifecycle execution proof
```

---

## 5. Generated runtime provenance does not become vulnerability identity

The published and installed package explicitly contained:

```text
npm-prepack-generated
scripts/generate-dist.js
/hidden/prepack-info
```

as provenance strings.

None appeared in any audit output.

So:

```text
runtime provenance
    !=
dependency identity
    !=
vulnerability visibility
```

---

## 6. A clean audit result does not describe the complete package-production history

The public lodash control proved the advisory service was working.

The absence of findings for S05 therefore means:

> npm found no known vulnerability for the dependency identities represented by the audit model.

It does not mean:

> npm inspected or reconstructed every piece of code or build-time action that produced the installed package.

---

# Final verdict

T07 demonstrates:

```text
package source
    !=
published package
    !=
npm dependency model
    !=
npm vulnerability result
```

and:

```text
prepack execution
    can generate shipped runtime code
    while the generator and input disappear
    without that provenance becoming visible
    to npm audit
```

The practical rule is:

> Treat `npm audit` as vulnerability analysis over npm dependency metadata, not as proof of how package bytes were produced or what lifecycle code executed during publication.
